# CLAUDE.md

Guidance for AI coding assistants working in `extension/`.

## Project

Chrome MV3 side-panel extension for **Koretex Browser Agent** — a vision-native browser agent that runs fully locally via Ollama. Forked from Nanobrowser but stripped to the shell: the multi-agent core, browser automation, and multi-provider LLM config were deleted. The agent core is rebuilt fresh phase by phase (see `../DESIGN.md`).

Current state: PLAN–ACT–VERIFY (PAV) architecture — perception (shadow-DOM-aware set-of-marks + screenshots), typed executor, Holo1.5-3B vision grounding, qwen2.5vl:3b visual verification, trajectory logging, cloud planner/reflector (GLM 5.2). A legacy fully-local Planner→Executor→Validator loop remains ONLY for the no-API-key case (`runLocalTask` in `agent/loop.ts`).

TWO CLOUD ENGINES, switched by the `CLOUD_ENGINE` constant in `agent/loop.ts` (currently 'stepwise' — an experiment being benched against 'pav'):

- STEPWISE (`agent/stepwise.ts`, prompts NEXT + REVIEW in orchestrator.ts): JUDGE-AND-DECIDE, one MULTIMODAL cloud call per step (`navigatorModel`, default qwen/qwen3.5-122b-a10b — user decision 2026-07-22: strongest open-weights multimodal, no OpenAI/Anthropic; xiaomi/mimo-v2.5 is the budget preset). Loop: capture screenshot + digest → the navigator JUDGES what the last action actually did (assessment + succeeded/failed/uncertain, from pixels) and DECIDES the next step → runtime executes → settle (per-action-type delay so the page reacts before it is photographed) → repeat until the navigator can SEE the objective delivered. NO planner-authored expects and no separate verifier — verification IS the judgment at the top of each turn. KICKOFF tier (strategic review #0): before the loop, ONE reasoning-ON call (no page context by design — intent, not mechanics) interprets what the user actually wants (class phrases → concrete searchable terms; live failure 2026-07-20: "decision makers" typed verbatim into LinkedIn search) and either sets the OPENING active strategy (≤4 sentences, pinned like any review strategy and freely superseded by later reviews), returns "proceed" for trivial/conversational objectives (triage folded in — no separate complexity call), or asks 1-3 clarifying questions (same awaiting_clarification flow; the answer resumes and re-runs kickoff with asking disabled). Skipped on stalled continuations; never consumes the reactive review budget. MULTI-TAB (tab-per-site, runtime-managed): the navigator only ever decides "navigate to <url>" — the conductor's tab manager (stepwise.ts navigateManaged, program.ts ctx.navigateTab/resolveTab) opens each new SITE in its own tab, and a later navigate to a known site SWITCHES to its tab (pure switch when the URL matches — state preserved, no reload; live failure 2026-07-20: single-tab thrash re-found the sheet via home and duplicated it). Site key = host (docs.google.com keyed per app path segment); cap 4 tabs/run then load-in-place; dialog guard arms per tab, CDP detaches from extras at task end; tabs stay open (deliverable may be one), scheduled runs' dedicated window closes them wholesale. The navigator sees a RUN TABS prompt line once ≥2 tabs exist. STRATEGIC REVIEW tier: the per-step loop is deliberately myopic; deterministic stuck signals (same action judged failed twice, 2 consecutive failed judgments, a guard rejection, ZERO-PROGRESS futility — PROGRESSLESS_STEPS(8) executed steps with no new collection item, no world-changing step, and no first visit to a new site (live 2026-07-21: ~25 ✓-judged re-searches, no stuck signal ever fired), or the navigator flagging "stuck": true) trigger ONE deep call — the STRATEGIST model (`strategistModel` setting, empty = orchestratorModel; user decision 2026-07-21: spend model quality generously on the strategic tier, kickoff + reviews, while the cheap navigator keeps the per-step load; a text-only strategist is fine — the review retries without the screenshot on image rejection) with reasoning ON — that diagnoses the root cause (e.g. a paywalled control that keeps reverting) and sets an ACTIVE STRATEGY, pinned into every subsequent turn until superseded. Review verdicts: strategy | done | blocked; review termination is OUTCOME-BASED (2026-07-23, user decision — no fixed budget): a dead end is two consecutive reviews with zero collection growth between them (measured via collectionMutations), a review repeating its predecessor's strategy stops the run honestly, and MAX_REVIEWS(8) is only a runaway backstop; at a dead end a run still progressing (progresslessSteps < 4) gets up to 3 grace passes (each clears the pacing window so the firing signal can't echo). The pacing detector (same action ≥3× in the 8-step window) is PROGRESS-GATED: it only escalates when progresslessSteps ≥ 4 — scroll→collect alternation with rows landing is convergence, never pacing. SWEEP EXECUTOR (2026-07-23, stepwise runSweep): full-page collection is a mechanical loop the harness owns — scroll-to-top, then per screenful ONE read → upsert rows → scroll down 1 viewport, bottom-detected by unchanged page signature ×2, capped at 30 screens, once per run. Reads are TEXT-FIRST (user decision 2026-07-23: text wherever possible, vision only as fallback): captureViewportText (extractPageText visibleOnly — one screenful of DOM text, lossless, ~5x cheaper) → collectFromText; a screen whose text route yields 0 items falls back to collectFromScreenshot at GROUNDER_SCREENSHOT_OPTS resolution (vision transcription misread ~15 cells in the all-vision run: Canva→"Canna", Klaviyo→"Alation"). Both readers share SWEEP_FIELD_RULES (each column holds only its own field; a "Title, Company" line splits at the LAST comma; illegible/absent field = omitted, never approximated); TRIGGERS (any of): a harvest landing <3 items, a collect landing ≥3 new rows on an open-ended collection (the list page is confirmed → gathering goes mechanical), or done declared on an open-ended collection without a prior sweep (EXHAUSTION GATE: sweep-adds-items → done REJECTED in code; adds nothing → exhaustion verified). SCROLL CLAMP: during open-ended gathering (openEndedGathering(): no schema target + all/full/every objective) scroll steps execute x1 regardless of decided times — multi-screen jumps skip content invisibly (the text reader failing on a page's card markup is a sensing problem, not a strategy problem — live 2026-07-23: harvest returned 1 then 0 on a page full of speaker cards and the navigator hand-cranked 40 steps of wandering scroll+collect). upsertRow strips a leading avatar-initials token from names ("DV Dor Vardi" → "Dor Vardi"). Budgets: wall clock 15 min is the working budget (navigator is told TIME REMAINING; MAX_STEPS=150 is only a runaway backstop), 4 consecutive judged failures, 3 CONSECUTIVE invalid decisions (any executed step resets). In-code guards: side-effect steps get one attempt; a side-effect judged failed/uncertain can never be re-issued on the same page (permanent per-run memory); an action judged failed twice is rejected at decision time and escalates to review; submit-looking click/key targets must declare sideEffect explicitly (input-looking targets exempt); clicks on human-verification controls (CAPTCHA_MARKERS regex) are ALWAYS rejected in code (live 2026-07-21: the navigator clicked Cloudflare's checkbox despite the prompt rule) — the `captchaBehavior` setting ('wait' default | 'stop') decides what follows: 'wait' parks the run on the challenge, focuses the agent window, polls perception (~4s, 3 min cap, 2 waits/run) until the USER clears it, then auto-resumes (same handoff wired into the navigator's stop decision and the review's blocked verdict when their reason matches the markers); 'stop'/timeout stalls with the standard reply-"continue" resume.
- PAV (`agent/pav.ts`): one cloud model makes every decision through PLAN (objective + journal + page digest → complete typed program, max 25 steps, each state-changing step carrying an `expect` postcondition + 1-4 objective-level expects), REFLECT (failed step + verifier observation → fix_step | replan | stop). The CONDUCTOR is a deterministic state machine — inner loop: execute step → verify expect → pass: next / fail: one silent retry, then REFLECT; outer loop: all steps passed → verify objective expects → achieved: REPORT / not: PLAN again with the journal, until MAX_PLANS (5) or the 15-min wall clock dies.

Both engines share REPORT (final answer; doubles as salvage; hard rule: URLs/emails/handles are reported only if observed on a page, never derived from names — live 2026-07-22: name-pattern-guessed "confirmed" websites; SCHEMA RUNS: the deliverable table in the final answer is rendered BY THE RUNTIME from the row store (stepwise renderMarkdownTable) and appended below the model's prose — the model is told NOT to reproduce it, because a model-retyped table silently drops rows at the output cap (live 2026-07-23: 107 curated rows → reply truncated at exactly 100 and narrated "100 speakers" as fact)) and CURATE (collection quality pass; stepwise runs it before the first collected-data write AND before every report, so off-qualifier items caught from hearsay sources are dropped before the answer; completeness breaks ties — a field-complete item beats an equally on-target one missing a required field). DONE AUDIT (stepwise, orchestrator.auditDone): when the navigator declares done AND a collection exists, a stronger model (strategistModel, page-blind) vets the claim against the FULL ledger before the run reports — counts per-item fields and item totals, and on "not complete" pins the actionable reason as the active strategy and continues (live 2026-07-22: done declared with 2 of 10 required websites); bounded MAX_DONE_AUDITS(2), a failed audit never blocks delivery. The navigator's own done rule now demands a COUNT ("7 of 10 items have a website") in its assessment, not a vague "several verified". NAVIGATOR sees the FULL collection each turn as THE LEDGER (COLLECTION_LEDGER_ITEMS=40 verbatim, was last-6 — the tail hid what was already held during per-item enrichment) with rules to check it before re-collecting/re-verifying and to enrich only items on it. CLICK-SPAWNED TABS: a click opening a target="_blank" tab (a "Visit Website" button, an outbound directory link) is adopted as currentTab before the next observation (chrome.tabs.onCreated, opener ∈ run tabs) so the agent follows the link like a person (live 2026-07-22: the official site the objective needed opened in a new tab the run never saw, forcing a slow per-company search fallback). Local models are senses only: label matching + Holo grounding resolve click targets, qwen3.5:4b reads pages (extract/harvest), `verifierModel` (qwen2.5vl:3b) answers visual questions.

LINKS APPENDIX (perception, 2026-07-21): extract/harvest page text carries a "LINKS ON PAGE (visible label — destination URL)" section (extractPageText's includeLinks arg, only on the capturePageText path — snapshot digests stay link-free) because a link renders as its label and the href was invisible to text extraction (live failure: "give me their websites" unanswerable through five extracts); the extractor prompt tells the reader to pair URLs with items only on a plain label match.

VERIFICATION (`agent/verifier.ts`): expects are tiered — `url` reads the tab itself (instant, no content script); `text`/`element`/`gone` are deterministic checks POLLED (~8s) against fresh perception (verification doubles as the wait-for-settle primitive; plans need no wait steps). A `text` expect matches page text OR element labels/placeholders (independent senses — heavy SPAs can return empty page text while the element digest is fine). `see` is one local-VLM screenshot question for canvas editors/visual outcomes. VISION ESCALATION (house rule: an uncertain sense escalates to a stronger sense, never concludes from blindness): when the deterministic senses were BLIND — no read at all, or empty page text for a text check, or an empty element digest for an element check — the verifier asks the local VLM one screenshot question derived from the expect before failing; vision only breaks ties where the alternative was certain failure. Conservative otherwise: uncertain = fail. Failures return a precise observation of what the page actually shows, including the underlying perception error when reads failed.

SAFETY IN CODE, NOT PROMPTS: steps tagged `sideEffect: true` (post/send/submit/purchase/delete) get exactly ONE attempt — never auto-retried; a reflect "fix" that repeats a failed side-effect action is rejected by the conductor. Loop guards: a fixed step that fails again forces replan; a plan whose action skeleton fingerprints identical to a failed plan gets one warning, then the run stops honestly. Plans without expects on state-changing steps are rejected by the conductor before execution.

SCHEMA'D COLLECTION (stepwise, 2026-07-22 — the architectural answer to the split-ledger class of bugs): KICKOFF may declare the deliverable as a TABLE (`deliverable: {columns, target}` — first column = the item's identifying name; target only when the objective names a count). The runtime then owns rows (`rows` + `rowIndex` in stepwise.ts): collect accepts OBJECT items keyed by columns (strings still parse via "Name — column: value" / bare-value type-matching — URLs fill the website-ish column, emails the mail-ish one); extract/harvest queries are auto-suffixed with the parseable line shape; same-name records MERGE into their row (filling empty cells only); completeness is COMPUTED (`rowComplete`/`completeRowCount`). The navigator sees a rendered DELIVERABLE TABLE section (status line + per-row [missing: …] annotations) instead of the raw ledger; "done" with target unmet is rejected IN CODE with the missing-cell list pinned as strategy (replaces the LLM done-audit, which still guards non-schema runs); curation picks which rows stay (matched by name) but rows remain the data; textFrom:"collected" writes get tab-separated column values; schema + rendered lines persist in runstate and round-trip on resume. No schema declared → exact previous free-text behavior. BATCH-LOOP EXECUTOR (built 2026-07-22, stepwise runBatchLoop): the strategist may attach `batchLoop {urlTemplate, fillColumn, maxIterations}` to a "strategy" verdict (REVIEW prompt documents it) — a codified per-row lookup the harness validates strictly (template contains {name} exactly once, https, fillColumn is a non-name table column, cap 40) and executes mechanically: navigateManaged the templated URL → settle → capturePageText (CAPTCHA_MARKERS abort; PII-scrubbed for cloud) → ONE reader call ("its OWN official … — never this page's domain"; linkish columns take the first external URL-ish token) → upsertRow, with 2 consecutive failures aborting back to normal stepping. Read-only by design: no clicks/typing/side-effects. DETERMINISTIC TRIGGER (once per run): ≥4 rows missing the same non-name column → one escalate() carrying "BATCH OPPORTUNITY: … reply with a batchLoop if a uniform lookup fits" (consumes a review slot); reviews fired for other reasons may also emit one. Trace shows "⚙ Batch: filling…" / "⚙ Batch done — N filled". Replaces ~4 multimodal calls per row with 1 cheap read per row.

DATA: the JOURNAL is one capped (~80 lines) append-only history fed identically to every cloud call — facts, step outcomes ✓/✗ with observations, reflect verdicts, data digests. The COLLECTION STORE keeps every extract's list lines deduped and UNTRUNCATED; SAME-ENTITY LINES MERGE (stepwise addOrUpgrade: lines sharing the entity head before the first field separator collapse into one line carrying the union of fields — live failure 2026-07-22: per-item enrichment stored "Name — website" beside "Name — Series A…" as partial twins and the pair never satisfied a per-item-fields objective; upgrades count as progress via a mutation counter, and the NEXT prompt tells the navigator to record upgrades as "Name — newfield"). NEVER-INVENT-DATA-INTO-FORMS rule in NEXT (live 2026-07-22: a fabricated email was submitted to an email-gate; gated content = wall on a fungible source, route around); write steps use `textFrom:"collected"` and the harness inserts all items verbatim at execution time (collected datasets never round-trip through the cloud). Harvest queries for data destined to be written must ask for items pre-formatted for the destination.

RESUME + CLARIFY + TIMEOUT: every cloud call goes through `background/net.ts` fetchWithTimeout (90s cap) so a stalled connection becomes a clean error, not a forever-spinner. PAV persists its knowledge (`runStateStore`, `packages/storage/lib/runstate/`) — objective + journal + collection + status — keyed by sessionId, after every plan and every verified step. On a stall/cancel/budget end the state is left status='stalled'; the next message on that session, if it is a CONTINUATION phrase ("continue"/"resume"/...), seeds the journal+collection and re-plans against the LIVE page (knowledge-replay, not step-replay — the stale page is re-observed). A delivered task clears its state; an unrelated new message discards the stale run. CLARIFY: PLAN may return mode "clarify" with 1-3 questions when the objective is genuinely ambiguous (first plan only); the conductor posts them, persists status='awaiting_clarification', and ends the turn — the user's next message is folded in as the answer and planning resumes. Prompt principle: ask ONLY when no reasonable default exists, else assume + note + proceed.

PRIVACY DOCTRINE (amended 2026-07-15, user decision — robustness first): the STEPWISE navigator sends tab SCREENSHOTS to the remote model; every orchestrator call requests no-retention routing (OpenRouter `provider: {data_collection: "deny"}`). Grounding (click coordinates) stays local by default. The PAV engine and the no-API-key local loop remain fully local — screenshots never leave the machine on those paths. Cloud payloads otherwise are digest-only: objective, journal, page digests (URL/title/element labels/text sample). Benchmark: `../bench/consistency/PROTOCOL.md`.

CLOUD-ONLY MODE + PII GUARD (settings `cloudOnly`/`cloudReaderModel`/`piiGuard`/`sensitiveSites`): with `cloudOnly` on, no Ollama is needed — extract/harvest reading routes to a cloud text model (planner's cloud `PlannerEndpoint`, cost tracked via `ctx.onUsage`) and click grounding + visual verification route to the navigator model through `callOrchestrator`; full page text then leaves the machine. The PII GUARD (`agent/pii.ts`, ON by default in cloud-only mode) pseudonymizes detectable identifiers (emails, Luhn-valid card numbers, SSNs, separator-bearing phone numbers — deliberately conservative so prices and IDs never match) into vault tokens (⟨email-1⟩) at the `callOrchestrator` choke point and before cloud reader calls; the executor REHYDRATES tokens to real values locally at typing time (`resolveStepText`) and in final answers — the cloud reasons over placeholders, the vault never leaves the machine (per-task, reset at run start). SENSITIVE-SITE POLICY (all stepwise runs): when the tab matches a `sensitiveSites` fragment and the host isn't approved for this task, the run pauses, explains that screenshots of the page would go to the cloud, and stalls; replying "continue" resumes AND approves that host for the task (`approvedHosts`/`pendingApprovalHost` in runstate). Screenshots are NOT covered by the PII guard — DOM-box field masking is a queued separate layer. Because screenshots show REAL values while objective/journal carry tokens, judge-facing prompts (NEXT/REVIEW) pin a PSEUDONYM TOKENS note whenever the vault is non-empty: a real identifier of matching type where a token was typed IS that token's value (live Gmail failure 2026-07-18: a correctly-typed recipient was judged "wrong email" against its token).

SKILLS (`agent/skills.ts`): small named playbooks of validated site knowledge — the canonical route to common operations plus the known traps (e.g. google-sheets: create via docs.google.com/spreadsheets/create, cell typing semantics, never select-all in a grid). A skill is a PRIOR, not a script: deterministically triggered (current tab host/path substring OR objective regex — the latter fires before the site is open) and pinned into the stepwise NEXT and REVIEW prompts as a SITE PLAYBOOKS section, same mechanism as ACTIVE STRATEGY; the navigator still judges every step from the live screenshot, and the page wins over any note it contradicts. House rule: skills carry only knowledge PAID FOR by live runs (post-mortems, strategic-review discoveries) — no speculation; site lore belongs here, never in the system prompts. Built-in playbook DATA lives in `packages/storage/lib/skills/builtins.ts` (serializable, shared with the options page, which renders built-ins alongside custom skills — editing one saves a same-named override to skillStore; "Restore built-in" removes it); `agent/skills.ts` compiles it and owns triggering/rendering. SKILLIFY (run → skill, `recorder/teach.ts`): a successful stepwise run stashes its objective + journal (chrome.storage.session, survives SW restarts) and the side panel offers a "Save as skill" button — but ONLY for novel runs: no playbook pinned, or a playbook pinned yet a strategic review still fired (the skill wasn't enough; the pinned names are passed to the distiller so it captures only the new knowledge, reusing an existing playbook name to update it); pressing it seeds the SAME distill → interview (objective question guaranteed in code) → review → save flow as teach-by-demonstration, with the distiller told the record is an agent-run journal (failed steps become trap lore). RECIPES (compositions of skills toward full objectives) come later — `packages/storage/lib/recipes/` storage remains for that phase.

AGENT MEMORY (`agent/memory.ts` + `packages/storage/lib/memory/`, 2026-07-25 — the soul.md idea): long-term identity + learnings that persist across ALL runs. Identity (agent name + "what I'll typically use it for") is set in onboarding (new "Meet your agent" step, saved on every exit path) and editable in the options Memory tab. LEARNINGS are rewritten WHOLE after every completed stepwise run (success AND failure) by one cheap distill call (`distillRunMemory`, navigator model, reasoning ON) fired-and-forgotten AFTER the final answer posts — never delays delivery; runs with <5 journal lines skip it (chat replies never distill). The distiller merges into three sections (WHAT WORKS / WHAT FAILS / ABOUT THE USER) under rules: merge-don't-append, every line earned by a run, general over specific, no secrets/PII/pseudonym-tokens; caps enforced IN CODE (`capLearnings`: 30 lines / 2400 chars), not prompt trust. Division of labor: SKILLS carry site lore, memory carries cross-task lore (user context/preferences, approach-level lessons) — the distiller is told to leave site specifics out. INJECTION: pinned as an AGENT MEMORY section into the STRATEGIC TIER ONLY — kickoff, strategic review, report (`memorySection` in orchestrator.ts) — never the per-step NEXT call (the opening strategy carries any relevant preference into the loop; memory would otherwise ride on up to 150 cheap calls). Objective outranks memory on conflict (stated in the kickoff prompt). Journal is already pseudonymized when distilled, so the memory call is as cloud-safe as the run's own calls; the options tab lets the user edit or "Forget learnings" wholesale.

EFFECTOR TRUTHFULNESS + PLATFORM (2026-07-25, from the Discord wrong-server run — 3 clicks aimed at the "K"/Koretex rail icon landed on another server, 2 strategic reviews prescribed strategy for a targeting defect, 2× Ctrl+K no-oped because macOS Discord binds Cmd+K): (1) `clickElementByIndex` (pageScript.ts) returns the accessible name + tag of the element ACTUALLY clicked and executor.ts echoes it in the exec note (`Clicked element [12] — hit "Solana Mobile Community" (a)`), so the judge sees target-vs-hit mismatch on the next turn instead of blaming the page; (2) `resolveTargetDetail` (program.ts) treats a ≤2-char target as AMBIGUOUS — forces the vision grounder, a label match cannot distinguish letter avatars; the NEXT prompt's DISAMBIGUATE rule now also bans glyph-named targets and tells the navigator to read the hit echo; (3) `platformLine()` (orchestrator.ts, chrome.runtime.getPlatformInfo cached at SW start) pins BROWSER OS into NEXT/REVIEW/kickoff — on macOS web-app shortcuts are Cmd/Meta, Ctrl+letter is usually a silent no-op (same blindness class as the missing date); (4) the discord playbook gained the paid-for traps (Nitro modal blocks the UI on load; the search bar opens a PREVIEW panel where channel clicks do nothing; verify the header names the intended server after a rail click); (5) memory distiller hardened: WHAT FAILS stores only OBSERVED action→result, never unconfirmed cause theories; ABOUT THE USER facts need an explicit user statement or a multi-run pattern (`runsDistilled` rides in the profile line). VALIDATED by the successful re-run (same task, 13 steps, $0.041): hit-echo let the judge name wrong-element clicks instantly, Meta+K opened the quick switcher first try. Follow-ups from that run (same day): memory distill moved to the STRATEGIST model with navigator fallback (the navigator model kept a disproven line and leaked site lore); discord playbook gained the validated quick-switcher route + the channel-link-vs-category-header trap ('#general' clicks hit the '💬 GENERAL' header); cloud grounding got `coerceXY` (grounding models answer {"point_2d":[x,y]}, bboxes, nested shapes — two "returned no coordinates" failures were shape mismatches, not missing answers); agentMemoryStore mutations are READ-FRESH MERGES + liveUpdate (createStorage's set(updater) runs against a once-per-context cache, so the SW's post-run applyLearnings clobbered the identity fields the options page had saved — beware this stale-cache class in ANY store written from multiple contexts, e.g. skillStore).

## Commands

Always use `pnpm` (v9, via corepack) with Node ≥ 22.12 (`nvm use v22.13.0`).

- `pnpm install` — install deps
- `pnpm build` — production build to `dist/`
- `pnpm dev` — watch mode with HMR
- `pnpm type-check` / `pnpm lint` / `pnpm prettier` — checks
- Workspace-scoped: `pnpm -F chrome-extension build`, `pnpm -F pages/side-panel type-check`, etc.

Load the extension: `chrome://extensions` → Developer mode → Load unpacked → `dist/`.

## Architecture

Turbo + pnpm monorepo:

- `chrome-extension/src/background/index.ts` — service worker: routes side-panel port messages (`new_task`, `follow_up_task`, `command`, `cancel_task`, `heartbeat`). Agent tasks run in a DEDICATED agent window (`taskWindow.ts`, user decision 2026-07-20) — never in the tab the user is browsing: visible 1290×900 window brought to the FRONT at task start (user decision 2026-07-22; was unfocused/hidden), reused across tasks (new tab per session; same session reuses its tab so "continue" re-observes the stalled page), left open at task end (the deliverable may be a tab); scheduled runs keep their own close-at-end window (schedules.ts). A companion TRACE VIEWER (the panel page in a popup window docked to the agent window's right edge, auto-closed with it) shows the live trace next to the driven tabs — chrome.sidePanel.open() needs a user gesture and silently failed, hence a popup; execution events broadcast to EVERY connected panel, only the originating panel persists to history, and a task aborts only when ALL panels close. Caveat: "this page"-style objectives no longer see the user's tab.
- `chrome-extension/src/background/agent/` — `loop.ts` (runAgentTask entry: routes to PAV or local-only; runSubtask legacy local loop), `pav.ts` (plan–act–verify conductor), `orchestrator.ts` (PLAN/REFLECT/REPORT cloud calls, digest-only), `verifier.ts` (tiered expect verification), `program.ts` (deterministic step engine, createStepRunner), `planner.ts` (local JSON-mode action selection + extract reader), `grounder.ts` (Holo grounding + verifyVisual), `chat.ts` (streaming chat), `prompts.ts`.
- `chrome-extension/src/background/actions/cdp.ts` — CDP escape hatch (Phase 6): trusted keyboard input via chrome.debugger for canvas editors (Google Docs/Sheets) that ignore synthetic events, plus SCREENSHOTS (`cdpCaptureScreenshot`) — CDP mouse is still avoided because the debugger infobar reflows the viewport and would shift grounder coordinates. `type_focused` action is CDP-only; `key` is CDP-first with synthetic fallback. Attach lazily, stay attached (stable geometry), detach at task end. Perception screenshots go through CDP whenever the tab is already attached (stepwise attaches at run start via armDialogGuard) so capture survives an unfocused/minimized window and always photographs the agent's tab; otherwise (quick commands, chat, local loop, attach failure) they use captureVisibleTab exactly as before — no infobar outside agent runs.
- `chrome-extension/src/background/perception/` — set-of-marks extraction (innermost-interactive dedupe, open shadow roots) + downscaled screenshots. Invariant: ONE extraction per step; executor never re-perceives (see executor.ts).
- `pages/side-panel/` — React chat UI. Connects via `chrome.runtime.connect({name: 'side-panel-connection'})`. Receives `execution` events (task.start/ok/fail/cancel), `stream_chunk` deltas, and `error`.
- `pages/options/` — settings page backed by `chatSettingsStore` (Ollama base URL + model; defaults `http://localhost:11434` / `qwen3.5:4b`).
- `packages/storage` — chrome.storage wrappers: `chatHistoryStore` (sessions/messages), `chatSettingsStore`, favorites. `Actors` = system | user | assistant.
- `packages/{ui,i18n,shared,vite-config,tailwind-config,tsconfig,hmr,dev-utils,zipper}` — tooling kept from upstream.

Message/actor types double as the future training-label schema — keep them typed and stable.

## Conventions

- Prettier: 2 spaces, single quotes, semicolons, printWidth 120. ESLint with `@typescript-eslint/consistent-type-imports`.
- Components `PascalCase`, variables `camelCase`, workspace dirs `kebab-case`.
- i18n: source locale is `packages/i18n/locales/en/messages.json`; never edit generated `packages/i18n/lib/**` or `dist/**`.
- Run `pnpm type-check` before committing.
- Keep extension permissions minimal (currently: storage, tabs, activeTab, scripting, unlimitedStorage, sidePanel, debugger — the last is the CDP escape hatch for trusted input; host permissions: <all_urls> for perception/actions + localhost Ollama).
